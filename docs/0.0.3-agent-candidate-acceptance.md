## 源码基线

## 自动化验收门禁
1. 严格文件清单、历史 APK/Via 资源哈希正确；
2. 全部回合执行、记忆、工作区、SSE 和流错误回归、严格 TypeScript、Playwright 与存储回归通过；
3. 原生 Java 编译与当前 Android Web 打包成功；
4. 使用固定且校验 SHA256 的 Apktool 及 Android 35 SDK 构建独立包，版本从 0.0.2/8 升为 0.0.3/10；
5. 只在前述门禁通过后从旧 Release 的**加密**签名备份与私有恢复 artifact 解密**同一** v0.0.2 证书。不得创建新密钥；用 `apksigner` 验证新旧证书完全一致、v2 签名、zipalign、包名及独立 Via provider；
6. 上传签名 APK 至短期私有 Actions artifact，而非覆盖正式 Release，删除 runner 内签名恢复材料，不记录密钥。

## 验收等级
自动化门禁通过仅代表 **CI/构建候选可用于安装测试**；不代表真实 DeepSeek/OpenRouter/Anthropic/Gemini 模型、手机网络/VPN、低内存进程杀死、备份恢复、跨多角色长时执行、安装升级中的用户数据保持已在真实机验收。正式发布需逐项提供实机证据。

本次不强制把 PR #12–#21 合并 main；这是故意的风险隔离，不要将未签名 APK、已有 0.0.2 安装包或模拟测试结果伪称为已验收新版本。签名候选使用已发布 0.0.2 独立包签名，目标升级包名 `chat.cloudlet.phone.v002`。与最初 0.0.1 原包名 `chat.cloudlet.phone` 分离。

## 2026-10-11 rc3 验收计划与实际界限

rc3 依赖 PR #29 → #28，使用 `release/agent-core-v003-rc3-20261011` 的单一源码提交生成 APK，versionCode=11、versionName=0.0.3、包名沿用 `chat.cloudlet.phone.v002`，保留 v0.0.2 同一签名，不覆盖任何旧 Release 或旧 rc2。

同一 GitHub Actions 工作流包含 `verify → package → android-upgrade` 串行门槛。Android 15/API35 模拟器只下载该次构建流程上传的签名 rc3 artifact，不再固定使用 rc2 artifact ID。验证签名 SHA、APK SHA、sourceCommit、包名、versionCode；从 0.0.2 原版离线 UI 写入合成纸条与草稿，冷启动后 `adb install -r` 覆盖升级，再检验记录与未发送草稿保留及重启。同步保存非敏感截图、日志与签名摘要。

**限制**：这是 Android 模拟器上的合成记录升级回归，不代表真机、VPN、真实 API、模型成本和复杂媒体队列验收。最终发布仍按 issue #15 审核，不从 rc3 构建工作流自动 Release。
