# 聊天执行器第一阶段：回合状态与故障隔离（2026-10-10）

## 合并顺序
本分支从 PR #18 通过全部 CI 的提交创建，属于 #13 的第一阶段。依赖关系：PR #12（网络）→ PR #18（运行时）→ 本 PR。勿跳过依赖，勿覆盖已发布 APK。

## 本轮已经实现
1. `lib/turn-execution.ts` 负责按发言人规划并执行一个会话回合。模型输出校验、可取消的自然延迟、角色校验、批量落盘、完成游标与附件处理从 `app/chat.tsx` 剥离。
2. 每位角色的一次回复所包含的所有文字气泡在**一次数据库提交**中写入，避免“上一条已存、下一条存储失败”的半完成状态；增加关系值仅发生一次。
3. 每位角色只发起一次推理请求。不自动格式修复或同义重生成；服务端异常以失败记录显示，允许用户手动恢复。
4. 内存待办队列按用户消息 **ID** 去重，保留跨对话线程的顺序和目标身份；去除仅在 AI 忙碌时才显示排队的错误状态。队列中的失效或已回答消息会在执行前清理。
5. 发送新文字消息必须先完成本机写入，才清空输入框并启动计费请求。界面切换和用户继续输入不会由旧写入完成后无条件擦掉新草稿。
6. 已经提交的角色文字不会因为随后可选媒体上传失败而再次自动发起模型调用；媒体失败另写提示。群聊失败时保留本次尚未完成发言人的恢复游标。
7. 新增 `scripts/verify-turn.mjs`，针对原子提交、重复消息 ID、失败回合、取消、角色变更、媒体错误和用户消息身份运行确定性测试，接入原有 CI 门禁。

## 本轮没有宣称完成的事项
- 目前排队表仍是会话存活期间的内存结构，**跨进程/网页重启不会自动续发**；这是一项刻意的安全约束，避免设备重启导致未知是否计费的 POST 自动重复。已保存的失败消息可由用户手动重试。
- 已经落盘的群聊消息仍采用原有 Schema；没有新增持久化 turnId/receipt，更精确的断点恢复与发送回执需要数据兼容性设计。
- 本轮没有构建 Hermes 式多 Agent 工具路由，不改角色卡、模型协议或外观。
- 仍须通过最新的严格 TypeScript、浏览器全量回归、Android 候选构建，以及后续目标 Android 实机与真实模型验收。

## 下一阶段建议
新增稳定的消息回合关联标识、只追加的可审计执行回执、受限工具调用、请求 token/费用预算和每角色独立工作空间。必须首先论证旧备份与数据库升级，且任何自动断点续传不能造成未知状态的重复模型计费。
