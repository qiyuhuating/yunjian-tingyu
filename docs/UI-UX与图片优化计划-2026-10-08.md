# 云笺听雨：UI、UX 与图片体积优化计划

日期：2026-10-08。审阅基线：qiyuhuating/yunjian-tingyu，main 提交 d280edd393b47834ab6a699747f714690d077c47。

## 结论与产品方向

保留插画、云朵小屋、四栏首页导航和陪伴氛围。当前最值得投入的是：保护未保存内容，缩短首次连接和再次聊天的路径，把界面操作与实际能力对齐，以及降低资源负担。增加更多应用入口的收益低于把聊天、角色、记忆、日记四条核心路径做好。

界面的辨识度已经成立：首页插画风格统一，浅色有纸面感，暗夜用中性灰而非单纯反色。聊天界面已经有单层标题、可见消息操作、图片预览、停止回复、草稿和本机保存恢复，不能把这些已完成的工作重复列为待办。

主要矛盾是：氛围界面与工具操作没有完全分层，设置页装载了过多概念，文字输入的保护规则不统一，运行时状态提示仍有歧义。应先修这些具体摩擦，再做视觉精修。

## 调研方法与证据范围

1. 核对 GitHub 当前文件树、资源字节数和重复 Git blob，读取前端 app、lib、Android Web 运行时、构建配置、验收脚本及既有 UI 报告。
2. 查看仓库保存的首页、设置、群聊和记忆截图；这些是历史交付证据，不替代本轮运行验证。
3. 获取六张主要插画原件并核对 Git blob SHA；比较优化 PNG 与 exact 无损 WebP。源码中的实际宽高、精灵裁切坐标均保留。
4. 分别构建原版 PNG 和优化 WebP 页面，在 Chromium 153 中操作首页、设置和聊天，检查 320、375、390、768、1440 宽度；验证图片 naturalWidth/naturalHeight、输入栏、横向溢出及草稿刷新恢复。
5. 运行 TypeScript 检查，以及 core、providers、voice、review、group、companion、context 七组，共 103 项核心检查。

本轮没有使用真实 Key 发起 AI 或通话，没有进行 Android 真机、签名 APK 更新、软键盘及低内存回收验收。桌宠浏览器检查使用禁用 WebGL的插画回退，不能代表 3D 性能。照片压缩没有改变用户聊天附件、头像或 PNG 内嵌角色卡。

## 首页与导航

保留现有日期、一起听、小纸条、四个插画入口与四栏底部导航。首页无需改成普通聊天 App，也无需新增大型宣传卡。

改动重点：

- 在现有聊天入口增加当前陪伴角色或最近会话的继续入口，目标是再次打开后一次操作接上上次聊天；首次用户仍能进入朋友列表。
- “全部应用”按聊天陪伴、生活记录、故事互动分组，保留搜索。论坛、朋友圈、微博可收进同一分组，减少概念重复，不自动删除已有数据。
- 所有返回动作明确区分关闭面板、返回列表、返回首页；离开编辑页面优先处理草稿。
- 矮屏优先保留核心入口和底部导航；让内容可滚动或收起装饰，避免依靠更小字号挤进一屏。
- 日期已在顶部文字与日历卡同时展示，后续只保留一处详细星期说明，给继续聊天留空间；四栏图标和绘图边界保持。

验收：390×844 常用内容不需要寻找；320 宽和横屏可完成核心动作；字号 200% 时不截断关键操作。五宽度现有布局已无横向溢出，应保持这个基线。

## 设置与首次使用

设置拆成可扫读的四组：连接 AI、聊天与声音、外观与个人资料、数据与备份。高级采样、世界书技术选项和核心提示词放进清楚命名的高级分区，保留现有能力。

连接流程：选择服务商 → 填 Key → 保留已选模型或读取列表 → 保存 → 可选测试。模型选择移动到保存按钮之前，让按钮真正保存当前看到的内容。区分“已保存配置”和“已测试可用”，header 的 AI 已配置不能让用户误以为网络连接已验证。

列表读取失败时仍能保存预设模型；重新读取和手动模型 ID 是次级操作。首次安装提供三个轻量入口：使用内置角色、导入角色、稍后连接。可以先探索离线内容，再配置服务。

自动记忆、摘要、重复重写可能增加模型调用。使用平实短说明和设置摘要，不把当前窗口、响应人数、提取频率全部挤在首次连接步骤。配置成功后给明确“开始聊天”的下一步。

## 聊天、群聊与记忆

1. 列表按置顶、未读、最近活动排序；当前只按未读优先、其他保留角色顺序。头像旁说明会话类型，最近消息摘要显示实际发送者。
2. 消息状态区分本地保存、排队、正在回复、回复中止、服务错误。用户点击停止不应看起来像网络失败，重试只作用于明确的那条请求。
3. 群聊等待期间可继续输入是已有能力，应保留；增加可见队列数与针对单条的取消。当前取消会清空 queued 数组，用户看不到受影响的等待消息。
4. 记忆和阶段摘要在回复循环中处理，busy 要到整理结束才释放。后续将“对方在回复”与“整理记忆”分开，避免正文发完仍显得在输入；背景任务必须保留原有来源校验和并发保护。
5. 为常用 @ 提供输入联想；保留点击群成员插入 @ 的现有行为。
6. 记忆抽屉强调角色或群归属、来源、日期、锁定状态；查看来源后能返回原聊天。世界书与提取记忆使用不同名称和说明，减少两种“记忆”的混淆。
7. 切换聊天、加载更早消息、出现新消息和修改字体时保持阅读位置；回到底部按钮保留。

大规模消息虚拟化应以实测为门槛：先用每会话 1,000/5,000/20,000 条消息检查输入、滚动、保存和内存，再决定是否替换现有 200 条分批呈现。图片压缩不降低原尺寸的解码内存，也不直接解决全状态 structuredClone 和遍历开销。

## 视觉与可访问性

首页可以继续使用衬线标题，聊天正文、表单及密集说明提供系统无衬线字体选项，代码固定等宽字体。Source Serif 4 的随包字体为拉丁字体，不能把中文显示一致性归功于它；中文实际依赖设备回退，需要 Android 真机比较字重、数字及标点。

统一一组文字层级、间距、圆角和表面变量。建议正文 15–16px、辅助文字 13–14px；既有主要操作 48px、消息菜单 44px 作为本产品目标保留，不把它混称为 WCAG AA 的唯一尺寸标准。

表单将“立即生效”和“需要保存”清楚区分。弹层逐步统一为可管理焦点的 dialog 或受控面板；当前图片预览已使用原生 dialog，其他 bottom-sheet 不应仅有外观而缺少焦点处理。加载、不可用、为空和错误状态各自有可行动的下一步。

低性能模式降低背景模糊和桌宠动画；reduced-motion 下除了 CSS 动画，也应停止没有必要的 WebGL 重绘。Pet3D 已跳过隐藏页面及不可见时的渲染，但 requestAnimationFrame 仍持续调度；减少动作时 t=0 仍重复 render，需实测耗电再改。

## 图片：本轮已经完成的压缩

选择 WebP 无损模式，exact=True、method=6、quality=100。这里的 quality 是无损编码努力参数，没有使用有损量化、缩放、调色板裁剪或 AI 重绘。保留 ICC（如存在），并验证解码后完整 RGBA 字节一致，包括 alpha=0 的区域。六张输入没有需要转换的 gamma/sRGB/chromaticity 声明；DPI 属于打印元数据，不用于网页 CSS 像素布局。

| button-sprite | 1774×887 | 1,313,405 | 920,416 | 29.92% |
| dock-sprite | 2172×724 | 1,571,700 | 1,064,052 | 32.30% |
| cloud-pet | 1374×1145 | 1,248,793 | 846,276 | 32.23% |
| music-listen | 1254×1254 | 1,200,508 | 706,036 | 41.19% |
| via-browser | 1254×1254 | 985,903 | 706,622 | 28.33% |
| wallpaper | 941×1672 | 1,822,518 | 1,396,454 | 23.38% |
| 合计 | 全部保持原尺寸 | 8,142,827 | 5,639,856 | 30.74% |

一套主要插画减少 2,502,971 字节，即约 2.39 MiB。独立解码的 RGBA 完全一致；Chromium 的 PNG/WebP 半透明预乘与取整路径仍有差异，叠在白、黑及暗夜底色上最多相差一个 8-bit 色阶，alpha 和不透明像素均一致，壁纸逐像素一致。这不是有损编码，但不能声称所有浏览器屏幕像素绝对相同，见 image-optimization-browser-pixels.json。优化 PNG 的收益逐图较低，图标的重新编码甚至变大，因此本轮选择六张插画的无损 WebP，192/512 安装图标继续保留 PNG。

特别注意：SpriteArt 中 dock 源尺寸 2172×724、button 源尺寸 1774×887 保持；ButtonArt 的浏览器绘图仍使用既有 1280 设计坐标，实际原图是 1254×1254。这是现有裁切设计与原图尺寸的差异，本轮只替换编码和路径，没有借压缩调整显示比例。

已更新源码中的插画引用，删除源码 public 中六份运行时旧 PNG，原件仍能从基线提交恢复。重复 Android 打包目录的旧资源及历史 APK/ZIP保持其交付身份；不是把原 APK 换个文件名就声称升级。

更换格式后，同样尺寸的解码纹理仍约占 width×height×4 的 RGBA 内存。六张合计约 36 MiB 理论像素缓冲（不代表实际峰值、GPU开销或所有图片同时驻留）；本次收益是文件和传输体积。

## 仓库体积与发布边界

源码 public 与 Android assets/web 包含重复的整套插画。更大的仓库体积还来自多份 APK 与源码 ZIP；GitHub 返回的 size=284178 是仓库元数据，不能等同当前 APK 大小或本地 checkout 体积。

后续推荐：

- 开发源码作为唯一资源源头，Android web 目录由构建生成，构建时只从已选资源复制，不同时塞进 PNG 和 WebP。
- APK、源码 ZIP、验收报告按 Releases 组织，主 README 指向明确的当前版本；旧交付先存档验证，再另行决定是否从分支工作树移除。
- 不在本轮删除历史交付，不重写 Git 历史。即使删除最新目录里的旧大文件，历史对象仍会保留，首次 clone 不一定按工作树下降。
- 本轮没有把截图压成有损格式，保留作为视觉证据；不压缩有内嵌人物设定文本的 PNG 角色卡，以免损坏其数据块。

现有 scripts/verify-delivery.py 强制 Android assets 与已签名 APK 逐字节一致。源码优化与正式交付需分阶段：本次验证产物写到独立输出目录；正式更新时用 android-web/vite.config.ts 生成新的 Android assets/web，再递增 versionCode、用既有私有签名构建 APK、更新资源校验、源码包与文件目录、完成设备验收。

不能只更新 Android assets 而继续让旧 APK 充当当前构建，也不能用调试签名冒充同签名覆盖升级。本次没有私有签名，不提供更新 APK；实际 APK 节省量待重新构建测量，不直接套用图片的 30.74%。

## 实施顺序与验收门槛

第一批：合入本轮图片源码补丁；实现日记/角色等草稿保护、设置模型状态修正、合并持久存储、修正文案与朗读按钮。验收以“不丢输入、入口与行为一致、首次连接能完成”为主。

第二批：消息搜索定位、继续聊天、附件快照、代码展示、单条排队与中止、删除撤销。验收覆盖慢解析、断网、重复点击、多会话切换、长代码、分页消息。

第三批：按模块整理 CSS 和状态，建立主题变量、编辑守卫、消息/后台任务状态模型；懒加载非核心模块，按实测处理全状态克隆和大历史遍历。保持当前本地备份、角色记忆隔离及固定核心契约。

第四批：重建签名 APK与发布产物。设备至少覆盖一个主流 Android 真机及一个较低性能设备；验证 WebView 120+、真实软键盘、字号放大、横屏、系统返回、后台恢复和备份。真实 Key 的费用、网络延迟和 Realtime 麦克风由实际授权环境验收。

每批独立提交，有可复现的验收结果再进入下一批；不一次重写全 App。合并门槛是对应行为已通过，不要求人为凑满测试数量。
