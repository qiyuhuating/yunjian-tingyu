## Spec：功能正确性与隐藏 bug

本轴 9 项：2 项 P1、7 项 P2。按本轴严重程度排列。

### F1 · P1：备份缺少关系校验，可使整个页面崩溃

位置：[phone-model.ts:12](mori-phone/lib/phone-model.ts)、[local-backup.ts:17](mori-phone/lib/local-backup.ts)、[phone.tsx:26](mori-phone/app/phone.tsx)、[phone.tsx:62](mori-phone/app/phone.tsx)。

`stateSchema` 只校验 primary 是字符串，不校验它指向现存角色。readBackup 接受这类 JSON；commit 先更新 React 状态，再由 writeLocal 检查默认角色关系。渲染已经先使用不存在的 companion，来不及显示保存错误。

复现：导出合法状态，只把 primary 改为 `missing-character`；在设置读取 JSON 并点击“恢复这份备份”。浏览器实际报错 `Cannot read properties of undefined (reading 'name')`，首页节点数量变为 0。

影响：无效备份能击穿恢复预览并使页面不可用。此复现没有证明原有磁盘记录被覆盖；writeLocal 的后置检查阻止了本次无效写入，重新打开仍有恢复机会。

建议：在任何内存替换和附件 staging 前统一校验默认角色、角色 ID 唯一性、群成员引用等关系；失败应保持当前状态。添加真实 UI 恢复回归测试。

### F2 · P1：Activity 重建会丢失文件导入、导出事务

位置：[MainActivity.java:22](android/src/chat/cloudlet/phone/MainActivity.java)、[:31](android/src/chat/cloudlet/phone/MainActivity.java)、[:117](android/src/chat/cloudlet/phone/MainActivity.java)、[AndroidManifest.xml:1](android/AndroidManifest.xml)。

picker、exportFile、exportId 只保存在 Activity 字段中；onCreate 忽略恢复 Bundle，Manifest 没有处理配置变化。系统文件选择或保存窗口打开后，旋转或进程重建会创建新实例；onActivityResult 只在原字段非空时处理结果，新实例会静默跳过。

影响：选择的附件不进入应用；创建的备份目标可能为空，缓存中的 .download 文件失去引用。源码与 Android 生命周期机制确认，尚无真机复现。Android 官方说明配置变化和进程重建需要保存状态：[Activity lifecycle](https://developer.android.com/guide/components/activities/activity-lifecycle)。

建议：恢复导出事务元数据并明确处理重新创建后的文件选择结果；不能只依靠阻止旋转掩盖进程重建。验收覆盖系统文件窗口中的旋转、返回和进程回收。

### F3 · P2：HTTP 204/205/304 会让原生请求一直悬挂

位置：[runtime.ts:8](mori-phone/android-web/runtime.ts)。

NativeHTTP.headers 对任何状态都创建 `new Response(job.stream, ...)`。这些空响应状态不允许附带 body，构造函数直接抛错，原 Promise 没有 resolve/reject。后续 end 清掉任务也无法补结算 Promise。

模拟实际 NativeHTTP 回调复现：204 产生 `Response with null body status cannot have body`，fetch 在超时探针中始终为 hung。影响是模型列表或兼容接口请求不能正常结束，也无法显示服务返回的状态。

建议：空响应状态使用 null body，并在所有回调异常路径结算请求和释放资源。覆盖 204、205、304、异常头和请求取消。

### F4 · P2：角色卡原样导出会丢失已导入的字段

位置：[character-import.ts:12](mori-phone/lib/character-import.ts)、[:89](mori-phone/lib/character-import.ts)。

导入保存原卡并提示长字段可原样导出，但 exportCharacter 仅对部分字段使用 keep。alternate_greetings、creator_notes、世界书 content 等直接被应用内截断值覆盖。

实际复现：31 个开场白导出后剩 30 个；作者说明和世界书正文各 18001 字，未修改任何设定，导出各剩 18000 字。已有长字段测试只覆盖 description，没有覆盖这些字段。

建议：未编辑字段沿用原始数据；已编辑字段使用用户的新值。不能仅凭字符串长度推断是否编辑。验收包括长字段、开场列表、标签和世界书的往返导入导出。

### F5 · P2：附件没有回收机制，删除和重复恢复持续占空间

位置：[local-phone.ts:26](mori-phone/lib/local-phone.ts)、[local-backup.ts:35](mori-phone/lib/local-backup.ts)、[music.tsx:8](mori-phone/app/music.tsx)。

assets 存储只有读取和写入，没有删除或垃圾回收路径。删除音乐只删除 state 引用；恢复备份每次写入新 UUID，旧文件仍保留；上传后记录校验失败也会留下孤立文件。

影响：长期使用和重复恢复会持续增大 IndexedDB，即使界面已经删除内容；最终可能触发配额不足、暂停所有状态保存。ZIP 只导出被引用文件，导出备份不会回收本机孤立文件。

建议：以当前已提交状态的引用集合为依据回收孤立文件，保护 staging、当前上传和失败恢复的清理过程；验收删除共享引用、失败恢复以及连续恢复同一备份。

### F6 · P2：删除全部群成员后留下不会回复的空群

位置：[characters.tsx:34](mori-phone/app/characters.tsx)、[phone-model.ts:14](mori-phone/lib/phone-model.ts)、[chat.tsx:27](mori-phone/app/chat.tsx)。

删除角色仅过滤群成员，保留空群；Schema 允许空成员数组。Chat 随后得到 speakers=[]，跳过全部 AI 请求。用户消息仍保存，界面没有回复，也不解释原因。

源码与 Node 分支验证确认。建议删除空群，或禁用发送并提供添加成员入口；备份关系校验也应处理空群。

### F7 · P2：朗读播放器没有所有权，回调可能串到下一条

位置：[use-voice.ts:6](mori-phone/app/use-voice.ts)、[runtime.ts:18](mori-phone/android-web/runtime.ts)、[MainActivity.java:75](android/src/chat/cloudlet/phone/MainActivity.java)。

每个 MessageCard 都创建 useVoice，任意阅读器卸载都会调用全局 speechSynthesis.cancel，能够取消另一个仍在使用的阅读器。原生朗读共用 cloudlet utterance ID，结束回调忽略 ID，运行时覆盖唯一 NativeSpeechEnd；旧事件如果迟到，只能调用新阅读器的结束处理。

影响：删除其他消息、短对话窗口移除旧消息等场景可能打断正在朗读的内容；播放 UI 与实际声音可能不同步。回调缺少身份已通过模拟验证；Android 事件竞争仍需真机验证。

建议：集中管理当前播放器，以唯一请求 ID 标记朗读；取消和清理必须仅作用于当前所有者，过期回调不得改变新任务状态。

### F8 · P2：失败的半截回答会进入下一轮模型上下文

位置：[chat.tsx:34](mori-phone/app/chat.tsx)、[chat-prompt.ts:11](mori-phone/lib/chat-prompt.ts)。

中止或断流时保存的半截回答带 failed=true，但 selectHistory 只过滤 system，不过滤失败的 assistant。Node 复现确认该记录再次被选入历史。recalledHistory 与 summaryPrompt 已过滤 failed，近期历史的策略却不同。

影响：被中止的错误内容成为下一轮普通 assistant 发言，可能干扰重试、延续错误事实或增加重复回答。

建议：保留用户提出的问题，排除失败 assistant；需要继续生成时使用明确的“继续”策略。验收主动取消、上游断流和重试。

### F9 · P2：后台摘要请求继承角色聊天约束

位置：[chat.tsx:32](mori-phone/app/chat.tsx)、[phone.tsx:47](mori-phone/app/phone.tsx)、[chat-prompt.ts:19](mori-phone/lib/chat-prompt.ts)。

summaryPrompt 虽然说明“后台摘要”，实际仍通过 requestAI 的 chat 路径。生成请求的系统指令要求只写角色台词动作、正文 60–160 字、不要复盘背景或重复总结；最后的补充消息又要求回应最近用户消息并可能附接话选项。它与提取事实摘要任务直接冲突。

实际请求构造检查确认这些指令同时存在；没有真实 Key 测试，因此不声称每次模型必然生成错误摘要。若模型输出聊天式内容，当前代码仍会保存为 continuity，并推进 through 游标，使该批历史不再进入下一次待摘要片段。

建议：为摘要使用独立任务提示和合适的输出预算，不继承角色扮演、选项或防重复指令；验证摘要结构和事实来源后再推进游标。

## 其他已验证边界和待验事项

- 原生 fetch 收到 Request 对象时只读取 URL，未继承 method、headers、body、signal。探针确认 POST + Authorization + body 变为 GET + 空头 + 空 body。当前业务多使用字符串 URL，此项列为兼容性隐患，不作为现有主路径故障计数；应按标准 Request 语义合并 init。
- 单线程历史硬上限 3000 条；第 3001 条被 Schema 拒绝，没有自动归档或新会话入口。限制本身不是死代码，但长期聊天的容量和恢复 UX 不完整。实际边界验证通过。
- 原生桥接暴露给 WebView 各 frame，外域子资源仍可默认联网，未设置内容安全策略。未发现现有用户内容能直接注入可执行 HTML 的路径，因此不报告“已可利用的攻击”。建议收紧 frame/导航来源并增加 CSP，参考 [Android native bridge guidance](https://developer.android.com/privacy-and-security/risks/insecure-webview-native-bridges)。
- 未发现完整 ZIP 直接导出 API Key；密钥在独立加密存储，备份不包含 keys/crypto 存储。
- 已检查字符卡 PNG 的 CRC、压缩文本输出上限，备份有附件 SHA-256 和尺寸检查；未把这些已存在的保护误报为缺失。
